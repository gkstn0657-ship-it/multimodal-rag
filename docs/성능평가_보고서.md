# 멀티모달 RAG 성능평가 보고서

## 개요

텍스트·스캔·표·차트가 섞인 문서(SDS KoPub VDR 40,781페이지, DART 공시 8,418페이지)를 대상으로 검색·생성 파이프라인을 구축하고 평가했습니다. 텍스트 레이어가 있는 페이지는 텍스트 그대로, 텍스트가 빈약한 페이지는 VLM(Vision-Language Model, 이미지와 텍스트를 함께 이해하는 모델. 여기서는 Qwen2.5-VL 사용) 캡셔닝(이미지를 보고 설명 텍스트를 생성하는 것)을 거쳐 인덱싱했고, 검색은 BGE-M3 밀집 임베딩(문장을 의미가 비슷할수록 가까운 위치에 놓는 숫자 벡터로 바꾸는 방식)과 BM25(단어가 얼마나 겹치는지로 점수를 매기는 전통적 검색 방식, 구글 이전 검색엔진의 기본 원리)를 RRF(Reciprocal Rank Fusion — 서로 다른 두 검색 결과의 순위를 합쳐 하나의 순위로 만드는 방법. "1등에 가까울수록 점수를 많이 준다"는 원리)로 결합한 하이브리드 방식을 씁니다.

## 용어 미리 보기

보고서 전체에서 반복되는 핵심 용어입니다. 해당 위치에서도 다시 짧게 설명하지만, 여기 모아둡니다.

| 용어 | 뜻 |
|---|---|
| Recall@k | 정답이 검색 결과 상위 k개 안에 들어왔는지 (0 또는 1). 여러 질문 평균을 낸 값 |
| MRR (Mean Reciprocal Rank) | 정답이 몇 번째 순위에 나왔는지의 역수(1위=1.0, 2위=0.5, 4위=0.25)를 평균한 값. 순위가 높을수록 점수가 큼 |
| nDCG (normalized Discounted Cumulative Gain) | Recall과 비슷하지만 "몇 위에 있었는지"를 로그 함수로 완만하게 반영하는 지표. 등급(정답/부분/무관)이 있을 때도 계산 가능 |
| 밀집 임베딩(dense embedding) | 문장·문서를 의미 기반 숫자 벡터로 바꾸는 방식. "가까운 벡터 = 비슷한 의미" |
| BM25 | 단어 일치 기반 검색. 의미는 몰라도 같은 단어(특히 고유명사·숫자)가 있으면 정확히 잡아냄 |
| 하이브리드 검색 | 밀집 임베딩과 BM25를 함께 써서 서로의 약점을 보완하는 방식 |
| 리랭커(reranker) | 1차로 후보를 넉넉히 뽑은 뒤, 질문과 후보 하나하나를 다시 비교해 순서를 정밀하게 재조정하는 2단계 모델 |
| 판정(judge) | 사람이 등급을 매기듯, AI가 "이 검색 결과가 실제로 질문에 답이 되는가"를 정답/부분/무관 세 등급으로 매기는 평가 방식 |
| 캡션(caption) | VLM이 이미지를 보고 만든 설명 텍스트. 이 텍스트를 검색 가능하게 만드는 다리 역할 |
| temperature 0 | 생성 모델이 매번 같은 입력에 같은 답을 내도록 무작위성을 최소화하는 설정 (평가 재현성을 위함) |
| 기권 게이트 | 검색 결과가 부실할 때 억지로 답하지 않고 "모른다"고 답하게 만드는 장치 (이번 평가에서는 채택하지 않음) |

## 파이프라인 최종 구성

```
문서 → 페이지 라우팅(TEXT/OCR/IMAGE/BLANK — 텍스트 유무·스캔 여부로 페이지를 4갈래로 분류)
     → IMAGE 경로만 VLM 전사 캡션(v3, 이미지 속 글자를 그대로 옮겨적는 방식) + OCR(광학 문자 인식) 합집합
     → BGE-M3 임베딩 + BM25(문서명·회사·사업연도 접두어 포함) 색인
     → 질의: 밀집 top-10 + BM25 top-10을 RRF로 병합
     → bge-reranker-v2-m3 재랭킹 → 상위 5개
     → VLM 답변 생성(상위 2개 청크는 원본 이미지 직접 투입)
```

여기까지 오는 동안 세 번 방향을 크게 틀었습니다. 캡션 프롬프트(VLM에게 캡션을 어떻게 쓰라고 지시하는 문구)는 창작(사실이 아닌 내용을 지어내는 것)을 막다가(v2) 검색 신호가 너무 짧아져(v3에서 전사 우선으로 재작성) 다시 손봤고, 검색은 밀집 임베딩 단독으로 시작했다가 회사명·연도 같은 고유명사가 안 잡히는 문제로 BM25를 얹었고, 그래도 남은 문제를 메타데이터(문서명·회사명·연도 같은 부가 정보) 접두어로 보완했습니다.

## 검색 성능

### SDS KoPub 라벨셋 (600문항, 자동 채점)

정답 페이지가 미리 정해져 있어 사람 채점 없이 자동으로 점수를 낼 수 있는 평가셋입니다.

| 지표 | 값 |
|---|---|
| Recall@1 (1위가 정답인 비율) | 0.448 |
| Recall@5 (상위 5개 안에 정답이 있는 비율) | 0.763 |
| Recall@10 | 0.852 |
| MRR | 0.579 |
| nDCG@5 | 0.616 |

라벨셋은 정답 페이지의 99.8%가 TEXT 경로(캡션 없이 원문 그대로 인덱싱된 페이지)라, 이 지표는 사실상 "이미지 처리를 다 빼고 일반 텍스트 RAG로서 얼마나 잘 되는가"를 봅니다. 하이브리드 검색을 넣기 전(밀집 임베딩 단독)에는 전체 Recall@1이 0.413이었는데, 하이브리드 적용 후 0.448로 올랐습니다.

### 합성 질의 (IMAGE 경로 194건에서 자체 생성, 자동 채점)

라벨셋만으로는 캡셔닝 효과를 검증할 수 없어서(정답이 IMAGE 경로인 문항이 600개 중 1개뿐) VLM이 IMAGE 경로 페이지를 보고 직접 질문을 만들게 해서 별도로 구축한 질의셋입니다.

| 구성 | Recall@5 | MRR | nDCG@5 |
|---|---|---|---|
| v2 캡션(창작 방지, 문장이 짧음) | 0.470 | 0.355 | 0.376 |
| v3 캡션+OCR, 밀집 임베딩 단독 | 0.524 | 0.402 | 0.425 |
| **v3 캡션+OCR, 하이브리드+접두어(최종)** | **0.681** | **0.502** | **0.543** |

v2에서 v3로 캡션 쓰는 방식을 바꾼 것보다 하이브리드 검색(BM25 추가)을 얹은 효과가 더 컸습니다. "이미지 속 정보를 더 정확히 텍스트로 옮기는 것"보다 "옮긴 텍스트를 정확히 찾아내는 것" 쪽이 더 큰 병목이었다는 뜻입니다.

### 사람이 실제로 물을 법한 질의 (42문항, LLM 판정)

위 두 자동 지표는 서로 다른 방향으로 편향돼 있습니다(라벨셋은 원문 그대로인 텍스트 페이지에 유리하고, 합성셋은 캡션에 쓰인 단어와 질문 단어가 겹치기 쉬워 캡션 쪽에 유리합니다). 이 편향을 피하려고 별도 검증을 했습니다. 판정은 답변을 생성한 모델(Qwen2.5-VL)과 다른 계열의 모델(Claude)이 맡아 자기 자신에게 유리하게 채점하는 위험을 피했고, 검색 결과 페이지 하나하나를 사람이 채점하듯 정답(2)/부분(1)/무관(0) 등급으로 매겼습니다.

| 유형 | 문항 수 | nDCG@5 | Recall@5(정답 등급 기준) | 무관 비율(관계없는 페이지가 섞인 비율) |
|---|---|---|---|---|
| 텍스트 | 5 | 0.910 | 1.00 | 0.12 |
| 표·차트(visual) | 5 | 0.974 | 0.80 | 0.24 |
| 복합(cross, 여러 문서를 종합해야 답할 수 있는 질문) | 5 | 0.931 | 1.00 | 0.08 |
| **IMAGE 경로** | 15 | 0.890 | **0.27** | 0.40 |

IMAGE 경로(이미지 캡셔닝을 거친 페이지)가 가장 약합니다. 원인을 뜯어보니 검색 자체는 나쁘지 않았습니다 — 정답 페이지를 80%는 찾아냈습니다(별도로 확인한 gold_in_top5 지표). 문제는 그 페이지 다수가 장 구분지·표지처럼 원래 담긴 정보가 없는 페이지였다는 점입니다. 페이지를 찾긴 찾았는데 그 페이지 자체에 답이 없었던 겁니다. 캡셔닝을 아무리 잘해도 없는 정보를 만들어낼 수는 없으니, 이건 캡션 품질 문제가 아니라 이 방식(이미지를 텍스트로 바꿔 검색하는 방식) 자체의 구조적 한계로 봅니다.

### DART 공시 문서 (10문항, 실사용형 질의, LLM 판정)

회사명·사업연도가 뒤섞인 실제 기업 공시 문서(DART, 금융감독원 전자공시시스템)로 별도 검증했습니다. "LG화학 2023년 배당금" 같은, 고유명사와 연도가 정확히 맞아야 답이 되는 질문 유형입니다.

| 구성 | Recall@5(정답 등급 기준) | 무관 비율 |
|---|---|---|
| 밀집 임베딩 단독 | 0.30 | 0.62 |
| + 하이브리드(BM25 추가) | 0.40 | 0.62 |
| + 문서명·회사·사업연도 접두어(검색용으로 페이지 텍스트 앞에 회사명·연도를 붙여주는 방법) | **0.50** | 0.62 |

접두어까지 넣어 목표(0.50)를 달성했지만, 무관 비율은 세 조합 모두 0.62로 그대로입니다. "LG화학을 물었는데 NAVER 페이지가 나온다" 같은 회사 자체가 다른 오류는 접두어로 줄었지만, "같은 회사의 다른 주제 페이지가 딸려온다"(예: 배당금을 물었는데 같은 회사 임원 명단 페이지가 나옴) 같은 문서 내부 혼동은 남아 있습니다. 검색 단계 신호(리랭크 점수, 1·2위 점수 격차, 후보 페이지들의 다양성)로 이런 경우를 걸러내는 기권 게이트를 시도했으나, 세 신호 모두 정답과 오답을 깨끗이 가르지 못해 채택하지 않았습니다.

## 생성 성능

15문항(text 5·cross 5·visual 5)을 두 조건으로 채점했습니다. **ours**는 원본 페이지 이미지를 VLM에 직접 투입하는 조건이고, **baseline**은 이미지 없이 텍스트(캡션 포함)만 주는 조건입니다 — 검색 결과는 두 조건이 완전히 동일하고, 오직 "VLM이 원본 이미지를 직접 보는가"만 다릅니다. 채점은 정확성(40)·완전성(25)·출처정확도(20)·간결성(15), 총 100점 배점으로 미리 정해둔 뒤 채점했고, 검색 판정과 마찬가지로 생성 모델과 다른 계열의 채점자가 맡았습니다.

| 유형 | ours | baseline | 차이 |
|---|---|---|---|
| 전체 | 64.6 | 62.5 | +2.1 |
| **표·차트(visual)** | **66.2** | **54.8** | **+11.4** |
| text | 62.4 | 66.6 | -4.2 |
| cross | 65.2 | 66.0 | -0.8 |

이미지 투입 효과는 표·차트 질문에서만 뚜렷하게 나타났습니다. 텍스트 질문에서는 애초에 투입할 이미지가 없어 두 조건이 사실상 같은 답을 냈고(같은 텍스트, 같은 프롬프트), 남은 작은 차이는 temperature 0(모델의 무작위성을 최소화하는 설정)에서도 완전히 사라지지 않는 생성 과정의 잔여 변동성으로 봅니다. "이미지가 필요한 곳에서만 이미지가 도움된다"는 설계 의도와 정확히 맞아떨어지는 결과입니다.

채점 과정에서 부작용 하나를 발견했습니다. 답변 뒤에 자기모순적으로 기권 문구("문서에서 찾을 수 없습니다")가 붙는 문제(과거에 한 번 고쳤던 것)가 특정 조건(기권 문구가 실제 답과 같은 문장에 붙는 경우)에서 재현됐습니다. 원인은 문구 제거 로직이 문장이 아니라 줄(line) 단위로만 동작해서, 실제 답과 기권 문구가 한 줄에 같이 있으면 그 줄 전체(실제 답 포함)가 지워져 버리는 것이었습니다. 문장 단위로 고치고 이 경우를 확인하는 테스트를 추가했습니다.

## 결론: 이 방식의 한계를 어디까지 확인했는가

이 파이프라인은 이미지를 VLM 캡션(텍스트)으로 바꿔 텍스트 임베딩에 넣는 방식입니다. 평가를 끝내고 보니 한계가 셋으로 갈립니다. 서로 원인이 달라서 섞어 쓰면 안 됩니다.

**첫째, 검색은 정답 페이지를 찍는데 그 페이지에 답이 없습니다.** 합성 IMAGE 질의에서 정답 페이지가 top-5에 든 비율은 80%인데, 그 안에 실제로 답을 담은 페이지가 있는 비율은 27%였습니다. 예를 들어 "제10절에서 재정계획의 목표는?"이라는 질문에 검색은 1위로 정답 페이지를 냈지만, 그 페이지는 "제10절 계획의 추진 및 재정계획"이라는 제목만 있는 간지였습니다(아산시 환경계획 586쪽). "5.3 항목의 시설물 이름은?"도 같습니다 — 1위가 정답 페이지였고, 페이지에는 "5.3 환경보전지역 및 시설물 현황"이라는 목차 한 줄만 있었습니다. IMAGE 경로 판정 15문항 중 10문항이 이 유형이었습니다. 이건 캡션이 정보를 놓친 게 아니라(캡션은 보이는 글자를 그대로 옮겼습니다) 페이지에 옮길 정보가 없는 것이라, 이미지를 직접 임베딩하는 방식으로 바꿔도 똑같이 남는 문제입니다. 코퍼스의 성질입니다.

**둘째, 캡션으로 옮기는 과정에서 정보가 실제로 빠집니다.** 이건 방식 자체의 손실이고 두 곳에서 실측됐습니다. 캡션 프롬프트 문구만 바꿔도(v2→v3) 같은 질의셋에서 Recall@5가 0.470에서 0.524로 움직였습니다 — 검색 성능이 이미지 내용이 아니라 "캡션이 무엇을 옮겼는가"에 좌우된다는 뜻입니다. 그리고 답변 단계에서 텍스트 대신 원본 이미지를 직접 보여주면 표·차트 질문 점수가 54.8에서 66.2로 올랐습니다 — 텍스트로 옮긴 것에는 없고 이미지에는 있는 정보가 있다는 뜻입니다. 이미지를 직접 임베딩하는 방식(ColPali·ColQwen2류)이 겨냥하는 손실이 바로 이것입니다. 다만 그 방식으로 같은 질의셋을 돌려보지는 않았으므로, "그 방식이 이 손실을 얼마나 회복하는가"는 아직 측정 전인 가설입니다.

**셋째, 같은 문서 안에서 주제가 다른 페이지를 못 가릅니다.** DART에서 회사·연도 불일치는 하이브리드와 접두어로 줄였지만, "같은 회사의 다른 주제 페이지"가 섞이는 무관 비율 0.62는 그대로였고, 검색 신호로 걸러내는 기권 게이트도 실패했습니다. 이건 캡션과 무관한 페이지 단위 관련성 판단 문제라, 방식을 바꿔도 남습니다.

정리하면 "캡션 방식은 유사한 문서만 찾고 정확한 문서는 못 찾는다"는 표현은 정확하지 않습니다. 정확한 페이지는 찾고 있습니다. 맞는 표현은 두 개입니다 — 찾은 페이지에 답이 없는 경우가 많고 그건 코퍼스 성질이라는 것, 그리고 캡션이 이미지 정보를 일부 떨어뜨리는 것은 실측됐고 그 손실을 이미지 직접 방식이 얼마나 회복하는지는 아직 재지 않았다는 것.

## 남은 한계

- IMAGE 경로 페이지 다수가 정보량이 적은 구분지·표지라, 캡셔닝 방식(이미지 → 텍스트 → 임베딩) 자체의 상한이 낮습니다. 이미지를 텍스트로 바꾸지 않고 그 자체로 벡터화하는 방식(ColPali·ColQwen2류, 이미지와 텍스트를 같은 벡터 공간에 직접 넣는 최신 기법)과 정면 비교하면 이 손실의 크기를 수치로 확인할 수 있는데, 아직 하지 않았습니다.
- DART 문서 내부의 "같은 회사, 다른 주제" 혼동은 검색 단계에서 못 잡았고, 검색 실패 시 답변을 내지 말아야 하는 기권 게이트도 아직 없습니다.
- 판정은 42문항, 생성 채점은 15문항으로 표본이 작습니다. 방향(어느 쪽이 더 나은가)은 뚜렷하지만 절대 수치의 신뢰구간은 넓게 봐야 합니다.
