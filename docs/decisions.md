# 설계 결정 기록

형식: 배경 → 결정 → 대가(트레이드오프). 결정을 뒤집을 때는 항목을 지우지 말고 아래에 새 항목을 추가한다.

## D-01. 서빙 엔진: vLLM → Ollama (2026-09-14)

- 배경: 개발 머신이 Windows 11이고 WSL이 설치되어 있지 않다(관리자 권한 없음). vLLM은 Linux 전용이다. Ollama 0.34이 이미 설치되어 있고 CUDA를 네이티브로 쓴다.
- 결정: Ollama로 Qwen2.5-VL을 서빙한다. OpenAI 호환 엔드포인트(`/v1`)를 쓰므로 파이프라인 코드는 서빙 엔진에 의존하지 않는다.
- 대가: vLLM의 연속 배칭이 없어 대량 캡셔닝 처리량이 낮다. Ollama는 요청을 순차 처리하므로 인덱싱은 단일 스트림으로 진행한다.

## D-02. VLM 크기: 7B 선택, 컨텍스트 8k → 4k (2026-09-14)

- 배경: 계획은 RTX 4070 12GB를 가정했으나 실제 GPU는 RTX 4070 Laptop 8GB다. Qwen2.5-VL-7B Q4는 가중치 약 5.5GB, 비전 인코더 약 0.7GB, 8k 컨텍스트 KV 캐시 약 1GB로 합계 약 7.5GB라 8GB에 겨우 들어간다. 3B는 여유가 있지만 표·차트의 숫자 전사 품질이 7B보다 눈에 띄게 낮다.
- 결정: 품질을 우선해 7B를 쓴다. 대신 컨텍스트를 4k로 줄여 KV 캐시를 절반으로 낮추고 GPU 상주 가능성을 높인다. 페이지 1장 캡셔닝은 비전 토큰 약 1,200개와 출력 500토큰 안팎이라 4k로 충분하다.
- 대가:
  1. 답변 단계에서 원본 페이지 이미지를 여러 장 넣을 수 없다. 이미지 투입 상한을 2장으로 두고 나머지 이미지 출신 청크는 캡션 텍스트로 대체한다.
  2. 캡셔닝 중에는 임베더·리랭커를 GPU에 올리지 않는다. 인덱싱은 "VLM 캡셔닝 → VLM 언로드 → GPU 임베딩" 순서로 분리 실행한다. 서빙 시점에는 VLM만 GPU, 임베더·리랭커는 CPU.
  3. 7B가 일부 CPU로 밀리면 페이지당 캡셔닝이 20초에서 40초 이상으로 늘 수 있다. Phase 0에서 실측하고, 40초를 넘기면 3B를 재검토한다.

- **추가 (2026-09-14, Phase 1 스모크 테스트 중 발견):** SDS KoPub 코퍼스의 실제 페이지 이미지는 약 300DPI(2480x3505px)로,
  원본 그대로 VLM에 넣으면 비전 토큰만 4,148개로 4k 컨텍스트를 초과해 요청이 거부됐다(실측 에러: `exceed_context_size_error`).
  `servers/vlm_client.py`에서 이미지의 긴 변을 1,280px로 다운스케일하는 전처리를 추가해 해결했다.
  대가: 매우 작은 글씨나 미세한 차트 눈금은 다운스케일 후 VLM이 잘못 읽을 수 있다 — 캡션 숫자 정확도 점검(Phase 1 검증)에서
  이 해상도로도 표 숫자를 정확히 읽는지 별도로 확인한다.

## D-03. 코퍼스: SDS KoPub VDR 1차, DART 2차 (2026-09-14)

- 근거와 대안 비교는 `docs/dataset.md`.
- 대가: 4만 페이지 전체를 캡셔닝할 수 없다(7B 기준 약 226시간). 텍스트 경로는 전체 인덱싱, 이미지 경로는 상한 3,000~5,000페이지로 제한한다. 상한 안에서 페이지를 고르는 규칙은 Phase 1에서 정한다.
