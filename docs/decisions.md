# 설계 결정 기록

형식: 배경 → 결정 → 대가(트레이드오프). 결정을 뒤집을 때는 항목을 지우지 말고 아래에 새 항목을 추가한다.

## D-01. 서빙 엔진: vLLM → Ollama (2026-09-14)

- 배경: 개발 머신이 Windows 11이고 WSL이 설치되어 있지 않다(관리자 권한 없음). vLLM은 Linux 전용이다. Ollama 0.34이 이미 설치되어 있고 CUDA를 네이티브로 쓴다.
- 결정: Ollama로 Qwen2.5-VL을 서빙한다. OpenAI 호환 엔드포인트(`/v1`)를 쓰므로 파이프라인 코드는 서빙 엔진에 의존하지 않는다.
- 대가: vLLM의 연속 배칭이 없어 대량 캡셔닝 처리량이 낮다. Ollama는 요청을 순차 처리하므로 인덱싱은 단일 스트림으로 진행한다.

## D-02. VLM 크기: 7B 선택, 컨텍스트 8k → 4k (2026-09-14)

- 배경: 계획은 RTX 4070 12GB를 가정했으나 실제 GPU는 RTX 4070 Laptop 8GB다. Qwen2.5-VL-7B Q4는 가중치 약 5.5GB, 비전 인코더 약 0.7GB, 8k 컨텍스트 KV 캐시 약 1GB로 합계 약 7.5GB라 8GB에 겨우 들어간다. 3B는 여유가 있지만 표·차트의 숫자 전사 품질이 7B보다 눈에 띄게 낮다.
- 결정: 품질을 우선해 7B를 쓴다. 대신 컨텍스트를 4k로 줄여 KV 캐시를 절반으로 낮추고 GPU 상주 가능성을 높인다. 페이지 1장 캡셔닝은 비전 토큰 약 1,200개와 출력 500토큰 안팎이라 4k로 충분하다.
- 대가:
  1. 답변 단계에서 원본 페이지 이미지를 여러 장 넣을 수 없다. 이미지 투입 상한을 2장으로 두고 나머지 이미지 출신 청크는 캡션 텍스트로 대체한다.
  2. 캡셔닝 중에는 임베더·리랭커를 GPU에 올리지 않는다. 인덱싱은 "VLM 캡셔닝 → VLM 언로드 → GPU 임베딩" 순서로 분리 실행한다. 서빙 시점에는 VLM만 GPU, 임베더·리랭커는 CPU.
  3. 7B가 일부 CPU로 밀리면 페이지당 캡셔닝이 20초에서 40초 이상으로 늘 수 있다. Phase 0에서 실측하고, 40초를 넘기면 3B를 재검토한다.

- **추가 (2026-09-14, Phase 1 스모크 테스트 중 발견):** SDS KoPub 코퍼스의 실제 페이지 이미지는 약 300DPI(2480x3505px)로,
  원본 그대로 VLM에 넣으면 비전 토큰만 4,148개로 4k 컨텍스트를 초과해 요청이 거부됐다(실측 에러: `exceed_context_size_error`).
  `servers/vlm_client.py`에서 이미지의 긴 변을 1,280px로 다운스케일하는 전처리를 추가해 해결했다.
  대가: 매우 작은 글씨나 미세한 차트 눈금은 다운스케일 후 VLM이 잘못 읽을 수 있다 — 캡션 숫자 정확도 점검(Phase 1 검증)에서
  이 해상도로도 표 숫자를 정확히 읽는지 별도로 확인한다.

## D-04. 라우팅 4갈래와 병렬 캡셔닝: 12시간 → 1시간 (2026-09-14)

- 배경: 500페이지 스모크 테스트에서 캡셔닝이 장당 평균 11.9초였다. 전체 코퍼스의 이미지 경로 3,707장(9.1%)을
  순차 처리하면 약 12시간. 목표는 2시간 이내.
- 실측:
  1. 이미지 경로 3,707장 중 OCR 텍스트가 100자 이상인 페이지 1,387장. 스캔된 본문 페이지라 OCR로 검색 가능하다.
  2. 텍스트·OCR 모두 20자 미만인 페이지 1,478장. 표본 84장 중 80장이 400px 썸네일 기준 잉크 비율 0.2% 미만인 백지.
  3. 캡션 시간은 출력 길이가 지배한다. 프리필 1,592토큰은 1~3초, 생성은 초당 약 30토큰. 549토큰 페이지는 17.6초.
  4. Ollama 병렬 요청: 4요청에서 장당 3.7초, 6요청에서 3.5초로 포화. 최대 VRAM 6.66GB / 8GB.
  5. 이미지를 1024px로 줄이면 프리필이 1,173토큰으로 줄지만 장당 0.3초 이득. 작은 글씨 판독 위험 대비 이득이 작아 1,280px 유지.
- 결정:
  1. 라우팅을 네 갈래로 나눈다. 텍스트 ≥100자 → TEXT. 아니면 OCR ≥100자 → OCR(VLM 생략). 아니면 잉크 <0.2% → BLANK(인덱싱 제외). 그 외 → IMAGE(VLM).
  2. 캡셔닝을 병렬 4로 돌리고 출력을 400토큰으로 제한한다.
  3. 캡션은 JSONL 캐시에 즉시 기록해 중단 후 재실행 시 이어간다. 페이지 단위 실패는 재시도 1회 후 OCR/텍스트로 대체하고 전체를 멈추지 않는다.
  4. OCR 경로 페이지도 원본 이미지를 디스크에 남겨, 답변 단계에서는 VLM이 스캔 원본을 직접 본다.
- 예상: VLM 대상 약 900장 × 3.7초 ≈ 1시간.
- 대가:
  1. OCR 경로로 보낸 1,387장 안에 표가 있으면 OCR이 행·열 구조를 평탄화한다. VLM 캡션이었다면 구조가 보존됐을 것이다.
     시간이 남으면 이 페이지들을 2차 캡셔닝하는 옵션을 남긴다.
  2. 백지 판정 임계값(0.2%)은 84장 표본 기준이다. 옅은 워터마크 페이지나 연한 도장만 있는 페이지가 백지로 분류될 수 있다.
  3. 출력 400토큰 제한으로 매우 큰 표는 뒷부분이 잘릴 수 있다.

  안 보이는 값은 "수치 불명"/"판독 불가"로 쓰게 하며, 사진 속 캡션·낙서·도장 문구를 최우선으로 옮기게

- 표 비율 급감이 정보 손실인지 확인하기 위해 v1에서 표였던 페이지 8장을 무작위로 뽑아 v2와 나란히

  - v1에서 처음 확인한 추가 창작 패턴 2건을 이 대조에서 발견: (1) 존재하지 않는 `imgur.com` 이미지
    URL을 표 안에 지어 넣음(2개 페이지에서 반복), (2) 시스템 프롬프트 지시문 자체("영문 테이블 헤더는
    그대로... 숫자는 그대로...")가 캡션 본문에 새어나옴. v2에서는 두 문제 모두 사라짐.

    바뀐 것이 표 비율 급감의 주 원인이며, 내용 자체는 동일하게 유지됨.
  - 존재하지 않는 "차트 x축/y축/추세" 서술도 v2에서 사라짐.
- 대가: 페이지 제목을 영어로 임의 번역하는 새로운 사소한 습관이 1건 관찰됨(제목 전체 번역, 표 헤더
  번역 금지 지시와는 별개 사례). 정보 손실은 아니나 다음 점검 때 확인 필요.

## D-10. 생성 품질 채점 결과: 비교가 샘플링 편차에 묻힘 (2026-09-16)

- 배경: `eval/judge_rubric.md`를 사전등록한 뒤 15문항(text 5 · cross 5 · visual 5) x 2조건(ours: 원본 이미지
  투입 / baseline: 텍스트만)을 Claude Fable 5.1(이 세션)이 채점했다. 결과는 `eval/generation_report.json`.
- 집계: ours 평균 43.5점, baseline 48.1점. 유형별 text 45.2 vs 57.6, cross 40.8 vs 40.8, visual 44.4 vs 45.8.
  ours가 이긴 문항 5, baseline 7, 동률 3.
- 그러나 이 집계는 두 조건의 차이를 말해주지 않는다. `eval/gen_eval_image_usage.json`으로 확인한 결과
  **15문항 중 이미지가 실제로 VLM에 들어간 문항은 3개**뿐이고, 그중 정답 페이지 이미지가 들어간 건 1번
  하나다(12·15번은 5위 OCR 청크의 무관한 이미지). 나머지 12문항은 두 조건의 프롬프트가 글자 하나까지
  같다. 그런데도 점수가 평균 10.4점(최대 34점, 2번 문항 62 vs 96) 벌어졌다 — Ollama 기본 temperature(0.8)
  에서 나오는 순수 샘플링 편차다. 즉 단일 샘플 채점으로는 조건 간 5점 차이를 해석할 수 없다.
- 이미지가 실제로 들어간 3문항만 따로 보면:
  - 1번(정답 페이지가 IMAGE 경로, 이미지 = 정답 페이지): ours 80 vs baseline 73. 이미지가 도움됐다.
  - 12번(5위 OCR 청크의 무관 이미지 투입): ours 8 vs baseline 34. 무관한 이미지가 답을 크게 망쳤다
    (존재하지 않는 참고문헌 창작).
  - 15번(5위 OCR 무관 이미지): ours 71 vs baseline 60. 편차 범위 안.
- 채점에서 드러난 생성 단계 결함(조건과 무관하게 발생):
  1. **D-09의 500자 절단이 정답을 잘라냈다.** 8번(암보험 민원 통계 607/588/673건)은 수치가 청크
     1,238자 위치, 12번(한약재 면세 한도 300g·150g·3kg·6병)은 884~1,250자 위치에 있었다. 둘 다 정답
     페이지가 1위로 검색됐는데도 답을 못 냈다.
  2. **퇴행 출력.** 14번(정수기)은 두 조건 모두 `@@@@…`만 출력했다. 당시 점검에서는 이상 문자를 못 찾았으나
     (제어문자·제로폭 기준으로만 봤음), 이후 D-12에서 CJK 호환 한자 U+F9CA가 원인임을 확인했다.
  3. **자기모순 마감.** 3·4·6번에서 답을 써놓고 끝에 "문서에서 찾을 수 없습니다"를 덧붙였다.
     시스템 프롬프트의 기권 지시가 과잉 적용된다.
  4. **깨진 토큰.** "스트로미", "압구당시", "쿠알아이더 교육 기 hội" 같은 언어 혼입이 산발적으로 나온다.
  5. **차트 수치 접근 불가.** 11번(ODA 유상/무상 그래프)은 정답 페이지가 TEXT 경로라 이미지가 VLM에
     들어가지 않았고, 그래프 값(350 vs 210)은 추출 텍스트에 없다. 텍스트가 100자 이상이면 차트가 있어도
     이미지 경로로 가지 않는 라우팅(D-04)의 맹점이다.
- 결론: 이 15문항 채점은 "이미지 투입 효과"에 대해 n=1의 방향성 사례(1번)만 준다. 대신 생성 단계의
  구체적 결함 5가지를 찾아냈고, 그중 1·2·"무관 이미지" 문제는 D-11에서 바로 고친다.

## D-11. 답변 생성 수정: 동적 컨텍스트 예산, 이미지 상위 순위 제한, temperature 0 (2026-09-16)

- 배경: D-10의 결함 1(500자 절단), 12번 사례(무관 이미지), 샘플링 편차.
- 결정:
  1. 500자 고정 절단(D-09)을 폐기하고, 텍스트 글자 예산을 `num_ctx - 답변 예약(500) - 오버헤드(200)
     - 이미지당 1,500토큰 x 이미지 수`로 계산해 재랭킹 순서대로 채운다(글자/토큰 1.5 가정, 청크당 최대
     2,500자). 이미지가 없는 대부분의 질의에서 예산이 약 5,000자로 늘어난다.
  2. 이미지는 재랭킹 상위 2위 안의 청크만 투입한다(`answer_image_max_rank`).
  3. 답변 생성 temperature를 0으로 고정한다. 평가 재현성이 목적이며, 서빙 품질에도 해롭지 않다.
- 검증(`eval/gen_eval_refix_check.txt`): 글자 예산은 이미지 0장 5,094자 / 1장 2,844자 / 2장 594자.
  - 8번(암보험 민원 통계): 607·588·673건 3/3 적중. 500자 절단 때는 0/3이었다.

## D-15. IMAGE 경로 임베딩 텍스트: 짧은 v2 캡션은 OCR보다 검색이 약함 → 전사 우선 캡션 + OCR (2026-09-16)

- 배경: SDS KoPub 라벨셋은 IMAGE 경로 정답이 1개뿐이라(D-08) 캡셔닝 효과를 재지 못했다. IMAGE 경로 997장 중
  200장을 뽑아 VLM이 페이지 이미지를 보고 질문 하나씩 쓰게 했다(`eval/synth_query_gen.py`, 필터 후 194건,
  `eval/synth_queries_image_pages.jsonl`). 정답은 그 페이지다. 질문 생성 모델이 캡셔너와 같은 Qwen2.5-VL이라
  캡션 저장소에 유리할 수 있는 조건이다.
- 실측(`eval/synth_query_report_variants.json`, IMAGE 997건의 임베딩 텍스트만 바꾼 저장소 비교):

  | 임베딩 텍스트 | Recall@1 | Recall@5 | Recall@10 | MRR |
  |---|---|---|---|---|
  | v2 캡션 (현재, D-07 보수적 프롬프트) | 26.3% | 45.9% | 53.6% | 0.350 |
  | OCR만 (`page.ocr or page.text`) | 32.0% | 52.1% | 57.2% | 0.397 |
  | v1 캡션 (D-07 이전, 장황·창작 있음) | 26.3% | 49.5% | 53.6% | 0.357 |
  | v2 캡션 + OCR | 27.8% | 45.4% | 52.1% | 0.361 |
  | v1 캡션 + OCR | 32.0% | 53.1% | 58.2% | 0.408 |

  문항별(v2 캡션 vs OCR): OCR 우세 46, 캡션 우세 32, 동률 116.
- 해석:
  1. 캡션에 유리한 조건에서도 **OCR 문자열이 v2 캡션을 이긴다.** IMAGE 경로 페이지의 OCR은 100자 미만의 짧은
     조각이지만 제목·기관명·연도처럼 질문이 그대로 재사용하는 글자를 담고 있다. v2 캡션은 창작을 막느라
     "표지입니다", "부록" 수준으로 짧아져(중앙값 84자) 그 글자들이 빠졌다. D-07의 대가가 여기서 드러났다.
  2. 장황한 v1 캡션이 v2보다 검색은 낫다. 그러나 v1은 없는 이름·숫자·URL을 만들어 냈으므로(D-07) 답변
     컨텍스트로 쓸 수 없다. "검색에 좋은 텍스트"와 "답변에 안전한 텍스트"가 갈린다.
  3. v2 캡션에 OCR을 붙여도 거의 안 오른다(MRR +0.011). 짧은 일반 문장이 OCR 신호를 희석한다.
  4. 캡션이 OCR을 이긴 사례는 OCR이 비어 있는 페이지(사진, 통계 구분지)였다. 캡션은 OCR이 못 읽는 페이지를
     메우는 역할로는 유효하다.
- 결정:
  1. 캡셔닝 프롬프트를 **전사 우선(v3)**으로 바꾼다(`indexing/caption.py`의 `CAPTION_PROMPT_V3`): 보이는 글자를
     전부 그대로 옮기고, 표는 행 단위 '항목: 값', 차트는 '범례: 수치'로, 해석은 마지막 '요약:' 한 문장으로만.
     창작 금지·판독 불가 표기는 D-07 그대로다. 검색 가능한 문자열과 창작 방지를 동시에 노린다.
  2. IMAGE 경로의 임베딩 텍스트를 **캡션 + OCR 합집합**으로 바꾼다(`indexing/embed_store.build_chunks`).
     OCR이 비어도 캡션이 남고, 캡션이 짧아도 OCR의 문자열이 남는다.
  3. 997장을 v3로 재캡셔닝(`indexing/recaption.py`, `data/captions_v3.jsonl`)한 뒤 같은 194문항으로 재측정한다.
     v1+OCR(53.1%)을 넘어야 성공이다.
- 대가: 전사 캡션은 길어져 캡셔닝 시간과 답변 컨텍스트 예산(D-11)을 더 쓴다. 표가 큰 페이지는 400토큰
  상한에서 잘릴 수 있다. 합성 질의는 같은 모델이 만들었으므로 절대 수치는 상한 추정치다 — 사람이 쓴 질의로는
  더 낮게 나올 수 있다.

## D-14. TEXT 경로 차트 페이지 감지: 저비용 픽셀 규칙으로는 불가 (부정 결과, 2026-09-16)

## D-12. 퇴행 출력 `@@@@…`의 원인: CJK 호환 한자 U+F9CA, NFKC 정규화와 자동 회복 (2026-09-16)

- 배경: 14번(정수기) 답변이 두 조건·temperature 0·0.8 모두 정확히 31개의 `@`였다. 원인을 단계적으로 좁혔다.
  1. 입력 변형 11종(줄바꿈 정규화, top-1 청크만, 시스템 프롬프트 제거, 질문만, 무관 청크, 질문 표현 변경 등)이
     전부 퇴행했고, "냉장고란 무엇인가?" 같은 컨트롤 단문까지 퇴행했다(`eval/gen_eval_q14_probe*.txt`).
     텍스트 전용 `qwen2.5:7b-instruct`는 정상. 이 구간의 응답은 모두 `usage.prompt_tokens == 0`이었다 —
     모델이 프롬프트를 처리하지 않고 반환한 것이다. Ollama 로그에는 같은 시간대(10:59)에 GPU 디스커버리
     워치독 타임아웃과 "unable to refresh free memory" 경고, 그 전(10:25)에 `llama-server terminated
     (exit status 1)` 크래시가 있었다.
  2. `ollama stop` 후 재로드하면 컨트롤 단문은 전부 정상. 그러나 14번 전체 프롬프트는 재시작 직후에도
     두 번 연속 퇴행했다(`eval/gen_eval_q14_after_restart.txt`). 즉 서버 저하와 별개로 이 프롬프트에
     결정적 트리거가 있다.
  3. 러너를 매번 새로 띄우고 이분했다(`eval/gen_eval_q14_bisect*.txt`, `gen_eval_q14_normalize.txt`):
     질문 단독 정상, 정수기 질문 + 정상 컨텍스트 정상, **정수기 본문 앞 200자만 붙이면 중립 질문으로도
     퇴행**(이때는 prompt_tokens=232로 처리된 뒤 퇴행). 뒤 120자에 트리거가 있었고, 줄바꿈·한자(U+4E00~9FFF)·
     중점 제거는 소용없었으며 **NFKC 정규화만 통과**했다.
  4. NFKC로 바뀌는 글자는 하나였다: "유입수(流入水)"의 **流 = U+F9CA, CJK COMPATIBILITY IDEOGRAPH-F9CA**.
     일반 한자 流(U+6D41)의 호환 코드포인트다. 한자 제거 정규식이 호환 한자 블록(U+F900~FAFF)을 안 덮어서
     3번 실험에서 살아남았다. 코퍼스 전체에서 2회, 2페이지에만 등장한다.
- 해석: Ollama/llama.cpp의 qwen2.5vl 토크나이저 경로가 이 호환 한자를 처리하지 못해 모델이 고정 토큰
  (`@` 반복)을 내는 것으로 보인다. 한 번 발생하면 이후 요청까지 `prompt_tokens=0`으로 퇴행하는 오염 상태가
  이어질 수 있고(NaN이 KV/프롬프트 캐시에 남는 방식으로 추정), 러너 재시작으로 회복된다. 텍스트 전용 모델은
  같은 글자를 정상 처리했다.
- 결정:
  1. `servers/answer.py`: 질문과 컨텍스트 텍스트를 VLM에 넣기 전에 NFKC 정규화한다(`normalize_for_vlm`).
     검증: 같은 200자를 NFKC만 적용해 넣으면 정상 요약이 나온다.
  2. `servers/vlm_client.py`: 퇴행 감지(글자 종류 2개 이하 또는 한 글자 80% 초과, 또는 `prompt_tokens == 0`)
     시 `ollama stop`으로 모델을 재시작하고 한 번 재시도한다. 두 번째도 퇴행이면 예외 → API 503.
     캡셔닝과 답변 생성 모두 적용. 단위 테스트 `tests/test_vlm_client.py`, `tests/test_answer.py`.
- 영향: D-10의 14번 0점(두 조건)은 모델 품질이 아니라 이 결함이다. `eval/generation_report.json`에 재분류하고,
  NFKC 적용 후 재생성한 답(`eval/gen_eval_q14_after_nfkc.txt`)으로 다시 채점한다.
- 대가: NFKC는 전각 영숫자·호환 기호도 함께 바꾼다(예: ㎏→kg, ①→1). 검색 임베딩은 원문 그대로 쓰므로
  영향이 없고 VLM 입력에만 적용된다. 트리거 글자가 희귀해(2/39,458) 재발은 드물겟지만, 다른 호환 문자도 같은
  문제를 일으킬 수 있어 감지·재시작 경로는 유지한다.

## D-09. 답변 생성 컨텍스트도 4k를 초과함 (2026-09-16)

- 배경: Phase 3 생성 품질 평가 표본(15문항)을 만들다가 첫 문항에서 `exceed_context_size_error`

  있는 매출·영업이익·제품 비중. 실패 7건 중 "LG화학 주당 배당금"에 NAVER 배당 페이지 5개가 나오는 등 회사명이
  다른 페이지가 상위에 오르는 사례가 반복됐고, "NAVER 2022 최대주주"에는 2023·2024 보고서 페이지만 나왔다.
  밀집 임베딩이 "배당" 의미는 잡지만 "LG화학"이라는 고유명사 일치를 보장하지 않는 전형적 실패로, BM25 하이브리드와
  회사·연도 접두어(Contextual Retrieval의 축소판)가 정확히 겨냥하는 지점이다. DART 무관@5 0.62는 SDS(0.08~0.44)보다
  훨씬 높다 — 한 회사의 500페이지 보고서 5개사 3개년이 서로 방해 문서가 되는 설계가 의도대로 작동했다.
- 표본 설계 오류: 답 없는 문항으로 넣은 J42("삼성전자 2021년 배당 결정")는 2022 보고서의 전기 비교 열에 2021
  배당이 있어 실제로는 답이 있었다. 등급은 사실대로(2) 매겼고, 답 없는 문항 오탐 1/2은 이 문항이다. 남은 답 없는
  문항(J41 "카카오 2025 상반기 매출")은 오탐 0.
- 결정: (1) v3 캡션+OCR을 운영 저장소로 채택한다 — 자동 지표에서 v2보다 낫고 판정에서 무관 비율이 가장 낮다.
  v1과의 2점 차이는 잡음이고 v1은 창작 위험(D-07)이 있다. (2) 다음 개선은 캡션 프롬프트가 아니라 검색 단계다:
  BM25 하이브리드 → 회사·연도·문서명 접두어 순으로 DART 10문항과 합성 185문항에서 재측정한다. (3) 합성 IMAGE
  질의셋은 "gold를 찾았나"가 아니라 판정 2등급 기준으로만 해석한다.
- 대가: 판정은 페이지 텍스트(캡션·OCR·본문 앞 1,500자) 기준이고 이미지를 직접 보지 않았다. 표·차트 값이 이미지에만
  있는 페이지는 과소평가될 수 있다. 판정자 오류 점검(표본 10% 사람 재확인)은 아직 하지 않았다.

## D-20. BM25 하이브리드(RRF) 추가: DART 회사·연도 혼동 완화 (2026-09-17)

- 배경: D-19에서 DART 실사용형 10문항 중 다수 실패가 회사명·연도가 다른 페이지 상위 노출이었다
  ("LG화학 배당금" 질의에 NAVER 페이지 5개, "NAVER 최대주주"에 다른 회사 보고서 등). 밀집 임베딩은
  "배당", "최대주주" 같은 의미는 잡지만 고유명사·연도 숫자의 정확한 일치는 보장하지 않는다.
- 결정: `indexing/bm25_index.py`(의존성 없는 numpy 구현, 소문자화 + 한글/영숫자 토큰화 + 흔한 조사 제거 +
  숫자·단위 분리)로 각 벡터 저장소 옆에 BM25 인덱스를 만들고, `servers/retrieve.py`의 `search()`에서
  벡터 top-k와 BM25 top-k를 RRF(`1/(60+rank)`)로 병합한다(`settings.hybrid_enabled`, 기본 켬. 저장소에
  `bm25.npz`가 없으면 자동으로 밀집 검색만 수행 — 하위 호환).
- 검증 1 (DART 판정): 10문항을 밀집 전용(`dart_dense`) vs 하이브리드(`dart_hybrid`)로 나눠 재실행하고,
  새로 등장한 16페이지만 추가 판정했다. **R@5(등급 2 기준) 0.30 → 0.40, nDCG@5 0.638 → 0.842**(같은 풀
  기준 IDCG — dense는 hybrid가 찾은 정답을 못 찾아 상대적으로 낮아짐). "LG화학 2023 주당 배당금"과
  "카카오 정정 사유" 2문항이 하이브리드에서만 정답(등급 2) 페이지를 top-5에 넣었다. n=10이라 통계적으로
  약하지만 방향은 설계 의도와 일치한다.
- 검증 2 (합성 IMAGE 질의 185건, 자동 지표): 하이브리드를 기본값으로 켠 뒤(BM25 인덱스가 있는 저장소는
  자동 적용) 재측정하니 **v3 캡션+OCR: Recall@5 0.524→0.681, MRR 0.402→0.502, nDCG@5 0.425→0.543**로
  D-19 대비 큰 폭 개선됐다. 같은 조건의 OCR 단독(0.568/0.439)·v2 캡션(0.557/0.398)보다도 앞선다
  (BM25 인덱스가 없는 v1 계열 저장소는 자동으로 밀집 전용 폴백이라 수치가 그대로임 — 폴백 동작 확인됨).
- 검증 3 (SDS KoPub 600문항, 자동 지표): 전체 Recall@1 0.413→0.448, Recall@10 0.830→0.852, MRR 0.563→0.579,
  nDCG@5 0.609→0.616. 특히 **visual 유형 Recall@5 0.646→0.689, MRR 0.434→0.502**로 캡셔닝이 필요한
  바로 그 유형에서 개선폭이 가장 크다. text/cross는 거의 그대로(이미 텍스트 일치로 잘 풀리던 문항이라
  하이브리드가 더할 게 적음 — 기대와 일치).
- 세 검증이 같은 방향이라(DART 실사용형, 합성 IMAGE, SDS 라벨셋 모두 개선) 이번 결정은 잡음이 아니라
  실제 효과로 판단한다.
- 대가: DART 무관 비율(0.62)은 그대로다 — 하이브리드는 회사·연도가 맞는 페이지를 더 끌어올리지만, 같은
  회사 안에서 주제가 다른 페이지(재무제표 각주, 임원 명단 등)까지 걸러내지는 못한다. 이건 다음 후보인
  회사·연도·문서명 메타데이터 접두어가 겨냥하는 문제다. 토크나이저가 형태소 분석기가 아니라 조사 처리가
  거칠고("네이버" vs "NAVER" 같은 표기 차이는 못 잡는다). DART는 판정 재실행까지 했지만 SDS는 자동
  지표만 다시 쟀고 판정(42문항)은 이전 결과(D-19)를 그대로 둔다 — 다음에 재채점할 때 갱신한다.

## D-21. 문서명·회사/사업연도 접두어를 BM25 색인에만 추가 (2026-09-17)

- 배경: D-20에서 하이브리드가 DART R@5는 올렸지만 무관 비율(0.62)은 그대로였다 — 회사·연도가 페이지
  본문에 없어서 벡터·BM25 둘 다 못 잡는 경우가 여전했다("LG화학 배당금"에 NAVER 페이지가 5개 중 4개).
  실행 전 계획(0→1단계, 성공/중단 기준 사전 확정)대로 진행했다.
- 결정: `indexing/doc_prefix.py`로 문서명 접두어를 만든다. SDS는 page_id에서 파일명을 추출(`sds_title`).
  DART는 `data/dart/manifest.jsonl`의 `report_nm`(사업연도·정정 여부 포함)과 파일명 첫 대괄호(회사명)를
  합쳐 `[회사] 보고서명(사업연도)` 형태로 만든다(`dart_prefix`) — 제출 연도가 아니라 사업연도를 쓰는 게
  핵심(카카오 2023년 폴더에 2020~2022 사업연도 정정본이 섞여 있어 파일명 연도만으로는 틀린다).
  0단계로 **BM25 색인에만** 접두어를 얹었다(`indexing/bm25_index.py --prefix`, 임베딩 텍스트·답변
  컨텍스트는 그대로) — 접두어가 밀집 벡터를 흐릴 위험을 피하려는 순서였다.
- 검증(사전 등록한 기준대로): DART 판정 10문항 **R@5(등급2) 0.40→0.50, nDCG@5 0.831→0.852**로 목표(≥0.50)
  달성. 부작용으로 추가된 8페이지 중 진짜 정답은 0건, 부분(등급1) 1건(LG화학 준법지원인 페이지 — 회사는
  맞지만 안건 자체는 아님) — **무관 비율은 목표(≤0.45)에 못 미치는 0.62 그대로**. 합성 IMAGE 질의
  185건은 R@5 0.681→0.665(−1.6점), MRR 0.502→0.494(−0.8점)로 계획한 중단 기준(3점 이상 하락)에는
  못 미치는 소폭 하락. SDS 600문항은 오히려 근소 개선(R@5 0.763→0.765, MRR 0.579→0.582).
- 1단계(밀집 임베딩 재임베딩) 보류 결정: 계획에서 1단계는 "0단계가 부족할 때만" 조건이었다. R@5 목표는
  달성했고, 못 채운 무관 비율은 "같은 회사 안 다른 주제" 문제라 접두어(문서 단위 신호)로는 애초에 못 푸는
  범주라고 판단한다 — 이건 페이지 단위 관련성 문제라 리랭커·기권 게이트가 맞는 도구다. 재임베딩(SDS
  16분·DART 4분)과 별도 저장소 유지 비용 대비 기대 효과가 작아 이번엔 넣지 않는다.
- 최종 상태: `data/vector_store`, `data/vector_store_dart`의 `bm25.npz`를 접두어 버전으로 교체했다(직전
  버전은 백업 후 검증하고 폐기 — 재현이 필요하면 `indexing/bm25_index.py <dir>`을 접두어 없이 다시 돌리면
  된다). `eval/report_v3.json`·`eval/synth_query_report_v3.json`을 이 최종 상태 기준으로 재생성했다.
- 대가: DART 무관 비율은 여전히 미해결 과제로 남긴다 — 기권 게이트(다음 순번)가 담당한다. SDS의 소폭 하락은
  감내 가능한 수준이지만, "문서명이 짧은 페이지의 검색 신호를 오히려 흐릴 수 있다"는 가설과 방향이 맞아
  접두어를 전 코퍼스에 일괄 적용할 때는 항상 이런 트레이드오프가 있다는 것을 기록해 둔다.

## D-22. 기권 게이트: 리랭크 1위 점수 단독 임계값은 쓸 수 없다 (부정 결과, 2026-09-17)

- 배경: D-20·D-21에서도 DART 무관 비율(0.62)이 그대로였다. "리랭크 1위 점수가 낮으면 VLM을 안 부르고
  기권한다"는 게이트를 설계하려고, 판정 표본 42문항을 현재 운영 설정(v3+하이브리드+접두어)으로 다시
  검색해 리랭크 1위 점수와 그 페이지의 등급(0/1/2, D-19 판정)을 묶었다(`eval/abstain_threshold.py`,
  `eval/abstain_threshold_report.json`). 새로 1위로 올라온 페이지 3장은 이번에 추가 판정했다.
- 발견: 점수와 등급이 거의 상관이 없다. **등급 2(정답)인 질의가 점수 0.07~0.40대에도 나오고**(J07=0.0695,
  J20=0.3977), **거꾸로 등급 0이거나 정답이 아예 없는 질의가 점수 0.66~0.99대로 나온다**(J42=0.6552,
  J34=0.9917 — gold가 있는데 못 찾은 채 자신만만하게 다른 페이지를 1위로 냄, J41=0.9588 — 애초에 답 없는
  질의). 임계값 후보를 0.05~0.80까지 스윕해도(위 표) 어떤 지점도 "정답은 통과, 오답/무답은 차단"을 깨끗이
  가르지 못한다 — th=0.80(표본 절반 가까이를 기권 처리하는 극단값)에서도 잡아내는 오답/무답은 5개 중
  2개뿐이고, 정답 17개 중 4개를 잘못 잘라낸다.
- 원인 해석: bge-reranker-v2-m3는 "질의와 페이지가 주제적으로 관련 있는가"에 점수를 매기지, "이 페이지
  하나로 질의에 답할 수 있는가"에 매기지 않는다. 그래서 같은 회사·같은 보고서·같은 문서 장르의 "얼추 비슷한"
  페이지에도 높은 점수를 준다(D-19~D-21이 계속 보고한 "무관하지만 리랭커는 통과시키는 페이지" 문제와
  같은 원인). 반대로 정답이 짧고 건조한 사실 나열(J07처럼)이면 리랭커가 오히려 낮게 채점한다.
- 결정: **단일 리랭크 점수 임계값 게이트는 도입하지 않는다.** 미검증 상태로 배포하면 실제로는 오답을
  거의 못 줄이면서 정답률만 깎는다 — D-14(픽셀 휴리스틱 기각)와 같은 종류의 정직한 부정 결과로 남긴다.
- 후속 후보(이번엔 미착수): (1) 1위·2위 점수 격차(margin) — "확실히 이거다" vs "고만고만한 후보들 중 하나"를
  구분할 가능성이 있다. (2) 판정 등급 데이터(42문항, 228페이지)로 작은 로지스틱 회귀를 학습해 점수·격차·
  route·질의 길이 등 여러 신호를 합치는 방법 — 다만 42문항은 이런 모델을 학습하기엔 너무 작다. (3) 애초에
  게이트를 리랭커가 아니라 "top-5 안에 서로 다른 회사/문서가 몇 개 섞였는가" 같은 D-19/D-21에서 이미 관찰한
  다양성 신호로 만드는 방법.
- 대가: D-13의 "검색 실패 시 무관 문서로 답변" 부작용은 이번에도 해결하지 못한 채 남는다. 다음에 이 문제를
  다시 다룰 때는 여기서 기록한 단일 점수 임계값을 반복하지 않는다.
- **후속(같은 날, 두 후보 신호 추가 검증):** D-22에서 제안한 두 후속 후보(1·2위 점수 격차, top-5 서로
  다른 문서 수)를 같은 42문항으로 마저 확인했다. 격차는 th=0.05에서 무관/무답 5건을 전부 잡지만 정답
  17건 중 10건을 잘못 자른다. 문서 다양성(`n_distinct_docs`)이 조금 낫다 — 임계 4개 이상이면 과잉기권
  5/17, 정상기권 포착 3/5로 다른 신호보다 균형이 나은 편이지만, 여전히 정답의 30%를 잘라내는 수준이라
  실전 게이트로 채택하기엔 부족하다. 세 신호(점수·격차·다양성) 모두 같은 결론으로 수렴한다 — **검색
  단계의 신호만으로는 "이 컨텍스트로 답할 수 있는가"를 판단할 수 없다.** 다음에 시도한다면 리랭커 점수가
  아니라, 답변 생성 직후 "방금 만든 답이 컨텍스트에 실제로 근거하는가"를 다시 한번 확인하는 생성 후
  검증(사후 체크) 쪽이 더 가능성 있다고 본다 — 이번 실험 범위 밖이라 다음 항목으로 남긴다.
- **마지막 시도 — 신호 조합(AND 규칙):** 단일 신호가 다 실패해서 두 신호를 겹쳐 봤다. 결과가 갈렸다.
  `문서 종류 ≥ 3 AND 격차 < 0.05`는 무관·무답 5건을 전부 잡지만 정답 17건 중 5건을 자르고(29%),
  **`문서 종류 ≥ 4 AND 격차 < 0.02`는 정답 17건 중 1건만 자르면서(6%) 무관·무답 5건 중 3건을 잡는다.**
  단일 신호로는 어느 조합도 못 냈던 균형이다. 해석: "top-5가 서로 다른 문서에서 왔고(주제가 흩어짐)
  1위가 2위와 구분이 안 된다(확신 없음)"는 두 조건이 동시에 성립할 때만 기권하는 규칙이라, 둘 중 하나만
  보면 생기는 오탐이 상쇄된다. top-5 점수 평균·표준편차는 신호가 되지 않았다.
- **그래도 채택하지 않는 이유:** 양성(기권해야 할) 표본이 5건뿐이고, 그중 J42는 D-19에서 확인한 대로
  실제로는 답이 있는 문항(4·5위가 등급 2)이라 사실상 4건이다. 4건 중 3건을 잡는 규칙은 우연으로도
  나올 수 있는 숫자다. 규칙 형태는 유력하지만 임계값(4, 0.02)은 이 표본에 맞춰진 것이라 그대로 배포하면
  D-13과 같은 "고쳤다고 생각했는데 부작용" 위험이 있다.
- **과제로 남김:** 답 없는 질의를 20~30개 더 만들어(회사·연도가 코퍼스 밖인 DART 질의, 코퍼스에 없는
  주제의 SDS 질의) 같은 42+N 문항으로 `문서 종류 ≥ k AND 격차 < m`의 k·m을 재선정하고, 과잉기권 10%
  이하·포착 70% 이상이면 `servers/answer.py`에 게이트로 넣는다. 그 전까지는 게이트 없이 운영한다.
  기권 게이트는 여기서 중단하고, 현재 파이프라인(v3 캡션+OCR, 하이브리드, 접두어)을 최종으로 확정한다.

## D-24. 생성 품질 재채점 및 자기모순 기권 수정의 사각지대 발견·수정 (2026-09-17)

- 배경: D-11~D-13 수정과 D-19~D-21(v3 운영 저장소, 하이브리드+접두어)이 반영된 현재 파이프라인으로
  `eval/gen_eval_sample.json` 15문항(text 5·cross 5·visual 5)을 ours(원본 이미지 투입)/baseline(텍스트만)
  두 조건으로 temperature 0에서 재생성(`eval/regen_gen_answers.py`)하고, 같은 사전등록 루브릭
  (`eval/judge_rubric.md`, 정확성40·완전성25·출처정확도20·간결성15)으로 다시 채점했다.
- 결과 (`eval/generation_report_v2.json`):

  | 유형 | ours | baseline |
  |---|---|---|
  | 전체(15문항) | 64.6 | 62.5 |
  | visual (5문항) | 66.2 | 54.8 |
  | text (5문항) | 62.4 | 66.6 |
  | cross (5문항) | 65.2 | 66.0 |

  ours가 전체적으로 소폭 앞서고(+2.1점), 격차는 거의 전부 visual 유형에서 난다(+11.4점) — 이미지가
  실제로 필요한 질문에서만 이미지 투입이 도움된다는, 설계 의도와 정확히 일치하는 결과다. text·cross는
  이미지가 없는 질문(검색된 청크 중 원본 이미지가 없거나 use_images 여부와 무관한 경우가 많음)이라
  큰 차이가 없거나 오히려 baseline이 근소 우세인데, 이는 temperature 0에서도 남는 잔차 비결정성
  (D-11에서 이미 관찰한 Ollama 프롬프트 캐시 영향)으로 보이며 실질적 차이로 보지 않는다.
- **부수 발견 — D-13 수정의 사각지대:** 문항 15(visual)의 baseline 답변이 "...중점을 둡니다.
  문서에서 찾을 수 없습니다."처럼 실제 답 뒤에 기권 문구가 **같은 줄, 같은 문단 안에서 문장만 바꿔**
  붙는 사례로 나왔다. `strip_contradictory_abstention`은 원래 **줄(line) 단위**로 기권 문구가 든 줄을
  통째로 지우는 방식이었는데, 이 경우 실제 답과 기권 문구가 한 줄에 같이 있어 그 줄 전체(실제 답 포함)가
  지워지고, 남은 내용이 `min_content_chars`(40자) 밑으로 떨어져 "정상 기권"으로 오판, 원본이 그대로
  반환되는 사각지대가 있었다 — 즉 D-13이 고치려던 자기모순이 이 케이스에서는 재현됐다.
- 결정: `strip_contradictory_abstention`을 줄 단위가 아니라 **문장 단위**(`.`, `!`, `?`, 줄바꿈 뒤 분리)로
  바꿔, 기권 문구가 든 문장만 제거하도록 고쳤다(`servers/answer.py`). 회귀 테스트
  (`test_same_line_trailing_abstention_is_removed`) 추가, 기존 D-13 테스트 포함 21개 전부 통과 확인.
- 그 외 관찰(수치 밖 정성 소견, 다음 개선 후보로만 기록):
  - 여러 문항(1,6,13)에서 답변이 `answer_max_tokens`(500) 안에서 문장 중간에 잘려 출처 표기까지
    못 가는 사례가 반복됐다 — 토큰 상한을 늘리거나, 출처를 본문 뒤가 아니라 구조화된 필드로 분리하는
    방안을 고려할 만하다.
  - 문항 7·11에서 검색이 질문의 실제 초점과 다른(주제는 겹치지만 각도가 다른) 문서를 회수해 답변이
    질문을 벗어난 사례가 있었다 — D-19~D-21이 겨냥한 "회사/문서 단위" 오류와는 다른, "같은 문서군 안
    하위 주제 혼동" 유형으로, 하이브리드·접두어로는 안 잡히는 범주다.
  - 문항 12에서 ours가 gold와 반대로 "멸종위기종 성분·오남용 의약품은 구매 금지"라고 잘못 단정한
    사실 오류가 나왔다 — 원본 이미지를 봤음에도 표의 단서(심사대상/처방전 수량 한정)를 놓친 사례로,
    이미지 투입이 항상 정확도를 높이는 것은 아니라는 반례로 남긴다.
- 대가: 채점 표본이 15문항으로 작아 유형별 평균(특히 ±10점대 차이)은 큰 신뢰구간을 감안해야 한다.
  문항 7·11처럼 검색 자체가 실패한 경우는 ours/baseline이 동일한 컨텍스트를 받으므로 이미지 투입
  효과를 전혀 반영하지 못한다 — 이런 문항을 표본에서 빼고 "검색이 맞은 문항만" 재분석하면 격차가
  더 크게 나올 가능성이 있으나, 사전등록 원칙(D-19)에 따라 표본을 사후에 걸러내지 않는다.

## D-25. 결론: "이미지 → 캡션 텍스트 → 임베딩" 방식의 한계를 어디까지 증명했는가 (2026-09-17)

- 배경: 이 프로젝트의 검색은 이미지를 VLM 캡션(텍스트)으로 바꿔 텍스트 임베딩 모델(BGE-M3)에 넣는
  방식이다(이하 "캡션 경유"). 이미지를 텍스트로 바꾸지 않고 직접 벡터화하는 방식(ColPali·ColQwen2류,
  이하 "이미지 직접")은 하드웨어 제약(D-02)으로 채택하지 않았다. 평가를 끝내고 나서 "캡션 경유의
  한계가 드러났다"고 정리하려는데, 실제로 무엇이 증명됐고 무엇이 아직 가설인지를 가르지 않으면
  과장이 된다. 여기에 분리해서 적는다.
- **증명된 것 1 — 검색은 페이지를 찍는데, 페이지에 답이 없다.** 합성 IMAGE 질의(D-19·D-23)에서 정답
  페이지가 top-5에 든 비율은 0.80인데, 그 top-5에 실제로 답을 담은 페이지(판정 등급 2)가 있는 비율은
  0.27이다. 원인은 IMAGE 경로(텍스트·OCR 100자 미만) 페이지의 다수가 장 구분지·표지·발표 제목
  슬라이드라 애초에 담긴 정보가 없기 때문이다. 이건 **캡션 방식의 한계가 아니라 코퍼스의 성질**이다 —
  없는 정보는 이미지 직접 방식으로도 못 찾는다.
- **증명된 것 2 — 캡션으로 옮기는 과정에서 정보가 빠진다.** (a) 캡션 프롬프트 문구만 바꿔도(v2→v3)
  같은 질의셋에서 Recall@5가 0.470→0.524로 움직였다(D-15) — 검색 성능이 "이미지 내용"이 아니라
  "캡션이 무엇을 옮겼는가"에 좌우된다는 뜻이다. (b) 답변 단계에서 텍스트 대신 원본 이미지를 직접
  보여주면 표·차트 질문 점수가 54.8→66.2로 올랐다(D-24) — 텍스트로 옮긴 것에는 없고 이미지에는
  있는 정보가 실제로 있다는 뜻이다. 이 두 관찰이 캡션 경유 방식 고유의 손실을 보여주는 근거다.
- **증명된 것 3 — 같은 문서 안에서 주제가 다른 페이지를 못 가른다.** DART 실사용형 질의에서 회사·연도
  불일치는 하이브리드·접두어(D-20·D-21)로 줄었지만, "같은 회사의 다른 주제 페이지"가 top-5에 섞이는
  무관 비율 0.62는 그대로였고 검색 신호 기반 기권 게이트도 실패했다(D-22). 이건 캡션 문제가 아니라
  페이지 단위 관련성 판단 문제로, 방식과 무관하게 남는 과제다.
- **아직 가설인 것 — 이미지 직접 방식이 위 2번 손실을 메운다.** 방식을 바꿔 같은 194문항을 돌려본
  적이 없다. 이미지 직접 방식이 페이지 안 정보를 더 잘 보존한다는 건 설계 원리상 그럴 법하지만, 이
  코퍼스·이 하드웨어에서 실제로 Recall이 오르는지는 측정 전이다. IMAGE 경로 997장만 대상으로 한
  대조 실험(선택 항목)이 이 가설을 검증하는 실험이다.
- 정리하면, "캡션 경유 방식은 유사한 문서만 찾고 정확한 문서는 못 찾는다"는 문장은 정확하지 않다.
  정확한 페이지는 찾고 있다. 맞는 문장은 두 개다 — (1) 찾은 페이지에 답이 없는 경우가 많고 이건
  코퍼스 성질이다, (2) 캡션이 이미지 정보를 일부 떨어뜨리는 것은 실측됐고, 그 손실을 이미지 직접
  방식이 얼마나 회복하는지는 아직 재지 않았다.
- 같은 날 테스트 화면을 붙였다(`servers/main.py`의 `/`, `servers/static/index.html`): 질의를 넣으면
  재랭킹 상위 5페이지의 텍스트·원본 이미지·점수와 생성 답변을 함께 보여준다. 위 한계를 눈으로 확인하는
  용도다 — 답변이 맞는지 근거 페이지를 직접 대조할 수 있다.

## D-26. 페이지 단위 검색의 두 가지 한계: 빈 페이지 반환과 절 단위 묶기의 이미지 문제 (2026-09-17)

- 배경: 테스트 화면(D-25)으로 직접 질의해 보며 확인된 한계 두 가지를 기록한다. 하나는 이미 수치로
  드러난 것(D-19·D-23)을 사용자가 눈으로 재확인한 것이고, 하나는 그 해결책으로 떠올린 방법이 이 파이프라인
  에서 막히는 지점이다.
- **한계 1 — 캡션 텍스트 임베딩은 표지·구분지 같은 "내용 없는 단일 페이지"를 정답으로 돌려준다.**
  IMAGE 경로 페이지(텍스트·OCR 100자 미만)의 캡션은 "○○ 장 표지, 제목 ○○" 식이 되고, 질의의 주제어와
  이 제목이 잘 맞아 검색 상위에 오른다. 그런데 그 페이지에는 제목 외의 정보가 없어 답변 근거가 되지 못한다.
  합성 IMAGE 질의 15문항 중 10문항이 이런 경우였고(정답 페이지 top-5 포함 0.80, 답을 담은 페이지 0.27,
  D-25 증명 1), 화면에서 질의해 보면 상위 5개가 표지·목차·장 구분지로 채워지는 사례를 그대로 볼 수 있다.
  검색 단위가 "페이지 1장"이고 페이지 안의 내용을 채점하지 않기 때문에 생기는 문제로, 이미지를 직접
  임베딩해도 그 페이지에 정보가 없다는 사실은 달라지지 않는다.
- **한계 2 — 텍스트 RAG에서 쓰던 시맨틱 청킹으로 페이지를 묶으려 했으나, 사이에 낀 이미지 페이지를
  다룰 수 없다.** 한계 1의 해법으로 "표지 뒤 본문 페이지들을 하나의 절(節)로 묶어 절 단위로 검색"하는
  방안을 검토했다. 단일 텍스트 RAG에서는 인접 문장의 임베딩 유사도가 급락하는 지점을 경계로 삼는 시맨틱
  청킹을 썼는데, 같은 방법을 여기에 옮기면 두 가지가 막힌다. (a) 경계 판정이 텍스트 임베딩 유사도에 의존
  하므로, 텍스트가 거의 없는 IMAGE 페이지(표·차트·스캔)는 앞뒤 페이지와의 유사도를 계산할 근거가 없어
  경계 판정에서 빠지거나 오판된다 — 바로 그 페이지가 묶어야 할 대상인데 묶는 기준에서 제외된다.
  (b) 묶은 뒤에도 문제가 남는다. 절 안에 텍스트 페이지와 이미지 페이지가 섞이면 절 하나의 임베딩을 어떻게
  만들지가 정해지지 않는다. 캡션 경유(방법 1)라면 캡션 텍스트를 이어붙여 텍스트 임베딩 하나로 만들 수
  있지만 캡션 손실(D-25 증명 2)이 그대로 들어가고, 이미지 직접 임베딩(방법 2)으로 바꾸면 절의 텍스트
  벡터와 이미지 벡터가 같은 공간에 있지 않아 하나로 합칠 수 없다. 즉 시맨틱 청킹은 텍스트 단일 모달을
  전제로 한 방법이고, 이미지가 사이에 끼는 순간 경계 판정과 표현 두 단계 모두에서 전제가 깨진다.
- 결정: 시맨틱 청킹(유사도 기반 경계)은 이 코퍼스에 채택하지 않는다. 절 단위 묶기를 한다면 경계는
  텍스트 유사도가 아니라 **문서 구조 신호**(장 구분지·표지 페이지 자체를 경계로 사용, 페이지 상단 반복
  머리글, DART 목차)로 잡고, 표현은 절을 하나의 벡터로 합치지 않고 **부모–자식 구조**(자식 = 기존
  페이지 단위 벡터로 검색, 부모 = 자식이 속한 절을 답변 컨텍스트로 반환)로 가져가는 것이 맞다. 이렇게
  하면 이미지 페이지는 기존 방식대로 각자 벡터를 갖고, 절 묶기는 검색이 아니라 "찍은 페이지 주변을 함께
  넘겨주는" 단계에서만 작동하므로 모달 혼합 문제를 피할 수 있다. 구현은 하지 않았고 과제로 남긴다.
  측정 대상은 구분지 정답 10문항(`eval/image_route_no_answer_examples.txt`)과 합성 185·SDS 600 회귀다.
