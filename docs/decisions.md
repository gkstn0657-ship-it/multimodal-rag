# 설계 결정 기록

형식: 배경 → 결정 → 대가(트레이드오프). 결정을 뒤집을 때는 항목을 지우지 말고 아래에 새 항목을 추가한다.

## D-01. 서빙 엔진: vLLM → Ollama (2026-09-14)

- 배경: 개발 머신이 Windows 11이고 WSL이 설치되어 있지 않다(관리자 권한 없음). vLLM은 Linux 전용이다. Ollama 0.34이 이미 설치되어 있고 CUDA를 네이티브로 쓴다.
- 결정: Ollama로 Qwen2.5-VL을 서빙한다. OpenAI 호환 엔드포인트(`/v1`)를 쓰므로 파이프라인 코드는 서빙 엔진에 의존하지 않는다.
- 대가: vLLM의 연속 배칭이 없어 대량 캡셔닝 처리량이 낮다. Ollama는 요청을 순차 처리하므로 인덱싱은 단일 스트림으로 진행한다.

## D-02. VLM 크기: 7B 선택, 컨텍스트 8k → 4k (2026-09-14)

- 배경: 계획은 RTX 4070 12GB를 가정했으나 실제 GPU는 RTX 4070 Laptop 8GB다. Qwen2.5-VL-7B Q4는 가중치 약 5.5GB, 비전 인코더 약 0.7GB, 8k 컨텍스트 KV 캐시 약 1GB로 합계 약 7.5GB라 8GB에 겨우 들어간다. 3B는 여유가 있지만 표·차트의 숫자 전사 품질이 7B보다 눈에 띄게 낮다.
- 결정: 품질을 우선해 7B를 쓴다. 대신 컨텍스트를 4k로 줄여 KV 캐시를 절반으로 낮추고 GPU 상주 가능성을 높인다. 페이지 1장 캡셔닝은 비전 토큰 약 1,200개와 출력 500토큰 안팎이라 4k로 충분하다.
- 대가:
  1. 답변 단계에서 원본 페이지 이미지를 여러 장 넣을 수 없다. 이미지 투입 상한을 2장으로 두고 나머지 이미지 출신 청크는 캡션 텍스트로 대체한다.
  2. 캡셔닝 중에는 임베더·리랭커를 GPU에 올리지 않는다. 인덱싱은 "VLM 캡셔닝 → VLM 언로드 → GPU 임베딩" 순서로 분리 실행한다. 서빙 시점에는 VLM만 GPU, 임베더·리랭커는 CPU.
  3. 7B가 일부 CPU로 밀리면 페이지당 캡셔닝이 20초에서 40초 이상으로 늘 수 있다. Phase 0에서 실측하고, 40초를 넘기면 3B를 재검토한다.

- **추가 (2026-09-14, Phase 1 스모크 테스트 중 발견):** SDS KoPub 코퍼스의 실제 페이지 이미지는 약 300DPI(2480x3505px)로,
  원본 그대로 VLM에 넣으면 비전 토큰만 4,148개로 4k 컨텍스트를 초과해 요청이 거부됐다(실측 에러: `exceed_context_size_error`).
  `servers/vlm_client.py`에서 이미지의 긴 변을 1,280px로 다운스케일하는 전처리를 추가해 해결했다.
  대가: 매우 작은 글씨나 미세한 차트 눈금은 다운스케일 후 VLM이 잘못 읽을 수 있다 — 캡션 숫자 정확도 점검(Phase 1 검증)에서
  이 해상도로도 표 숫자를 정확히 읽는지 별도로 확인한다.

## D-04. 라우팅 4갈래와 병렬 캡셔닝: 12시간 → 1시간 (2026-09-14)

- 배경: 500페이지 스모크 테스트에서 캡셔닝이 장당 평균 11.9초였다. 전체 코퍼스의 이미지 경로 3,707장(9.1%)을
  순차 처리하면 약 12시간. 목표는 2시간 이내.
- 실측:
  1. 이미지 경로 3,707장 중 OCR 텍스트가 100자 이상인 페이지 1,387장. 스캔된 본문 페이지라 OCR로 검색 가능하다.
  2. 텍스트·OCR 모두 20자 미만인 페이지 1,478장. 표본 84장 중 80장이 400px 썸네일 기준 잉크 비율 0.2% 미만인 백지.
  3. 캡션 시간은 출력 길이가 지배한다. 프리필 1,592토큰은 1~3초, 생성은 초당 약 30토큰. 549토큰 페이지는 17.6초.
  4. Ollama 병렬 요청: 4요청에서 장당 3.7초, 6요청에서 3.5초로 포화. 최대 VRAM 6.66GB / 8GB.
  5. 이미지를 1024px로 줄이면 프리필이 1,173토큰으로 줄지만 장당 0.3초 이득. 작은 글씨 판독 위험 대비 이득이 작아 1,280px 유지.
- 결정:
  1. 라우팅을 네 갈래로 나눈다. 텍스트 ≥100자 → TEXT. 아니면 OCR ≥100자 → OCR(VLM 생략). 아니면 잉크 <0.2% → BLANK(인덱싱 제외). 그 외 → IMAGE(VLM).
  2. 캡셔닝을 병렬 4로 돌리고 출력을 400토큰으로 제한한다.
  3. 캡션은 JSONL 캐시에 즉시 기록해 중단 후 재실행 시 이어간다. 페이지 단위 실패는 재시도 1회 후 OCR/텍스트로 대체하고 전체를 멈추지 않는다.
  4. OCR 경로 페이지도 원본 이미지를 디스크에 남겨, 답변 단계에서는 VLM이 스캔 원본을 직접 본다.
- 예상: VLM 대상 약 900장 × 3.7초 ≈ 1시간.
- 대가:
  1. OCR 경로로 보낸 1,387장 안에 표가 있으면 OCR이 행·열 구조를 평탄화한다. VLM 캡션이었다면 구조가 보존됐을 것이다.
     시간이 남으면 이 페이지들을 2차 캡셔닝하는 옵션을 남긴다.
  2. 백지 판정 임계값(0.2%)은 84장 표본 기준이다. 옅은 워터마크 페이지나 연한 도장만 있는 페이지가 백지로 분류될 수 있다.
  3. 출력 400토큰 제한으로 매우 큰 표는 뒷부분이 잘릴 수 있다.

## D-07. 캡셔닝 프롬프트: 표·수치 창작 방지 (2026-09-15)

- 배경: IMAGE 경로 997장 중 표 형식(`|`) 캡션 130장에서 10장을 무작위 표본으로 뽑아 원본 페이지 이미지와
  직접 대조했다. 5장을 상세 검토한 결과:
  - 광복군 포대(민간기록물) 사진: 페이지의 유일한 실제 정보인 사진 캡션 문구("2021 민간기록물 수집
    공모전 대상 - 광복군 포대(남궁승영 소장)")를 놓치고, 이미지에 없는 이름("南雲鐵", "张德生")과
    숫자("NO. 3613")를 창작했다.
  - 울산광역시 정보화 기본계획 표지: 제목과 기간(2024-2028)만 있는 표지인데 연도별 세부 계획 5행 표를
    통째로 창작했다.
  - 다문화사회통합전략 부록 구분지: "페이지는 비어 있다"고 쓴 바로 다음 줄에 존재하지 않는 표 2개를
    만들어냈다(자기모순).
  - 동구 성인지 통계: 실제 수치("4.6")는 정확히 옮겼으나 존재하지 않는 "증가 추세 그래프" 서술을 덧붙였다.
  - 파주스포츠센터 성과평가: 실제로는 번호 목록(①②③)인데 빈 칸투성이 표로 왜곡했다.
  - 표본 10장 중 5장 상세검토에서 2장 심각한 창작, 1장 자기모순, 1장 근거 없는 서술 추가, 1장 형식 왜곡.
- 원인: 캡셔닝 프롬프트("표는 마크다운으로 유지하라")가 표가 없는 페이지에도 적용되어, VLM이 형식을
  맞추려 내용을 지어내는 경향을 유발했다.
- 결정: `indexing/caption.py`의 `CAPTION_PROMPT`를 수정한다. 실제로 표·차트가 있을 때만 표를 만들고,
  안 보이는 값은 "수치 불명"/"판독 불가"로 쓰게 하며, 사진 속 캡션·낙서·도장 문구를 최우선으로 옮기게
  하고, 장식용 디자인 요소는 무시하게 했다. 파이프라인 구조는 건드리지 않았다(`docs/plan.md` Phase 1 원칙).
- 검증: 문제였던 5장에 새 프롬프트를 그대로 재적용해 전부 정상화됨을 확인(광복군 포대 캡션 정상 인식,
  창작된 표 전부 사라짐, 목록을 표로 왜곡하지 않음). 이후 997장 전체를 새 프롬프트로 재캡셔닝했다.
  기존 캡션은 `data/captions_v1_backup.jsonl`로 보관한다(비교 참고용, git 제외).
- 대가: 표가 실제로 있는 페이지에서도 VLM이 더 보수적으로 "수치 불명"을 남발할 가능성이 있다. 재캡셔닝
  결과에서 이 비율을 확인해야 한다.
