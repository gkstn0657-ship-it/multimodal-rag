# 설계 결정 기록

형식: 배경 → 결정 → 대가(트레이드오프). 결정을 뒤집을 때는 항목을 지우지 말고 아래에 새 항목을 추가한다.

## D-01. 서빙 엔진: vLLM → Ollama (2026-09-14)

- 배경: 개발 머신이 Windows 11이고 WSL이 설치되어 있지 않다(관리자 권한 없음). vLLM은 Linux 전용이다. Ollama 0.34이 이미 설치되어 있고 CUDA를 네이티브로 쓴다.
- 결정: Ollama로 Qwen2.5-VL을 서빙한다. OpenAI 호환 엔드포인트(`/v1`)를 쓰므로 파이프라인 코드는 서빙 엔진에 의존하지 않는다.
- 대가: vLLM의 연속 배칭이 없어 대량 캡셔닝 처리량이 낮다. Ollama는 요청을 순차 처리하므로 인덱싱은 단일 스트림으로 진행한다.

## D-02. VLM 크기: 7B 선택, 컨텍스트 8k → 4k (2026-09-14)

- 배경: 계획은 RTX 4070 12GB를 가정했으나 실제 GPU는 RTX 4070 Laptop 8GB다. Qwen2.5-VL-7B Q4는 가중치 약 5.5GB, 비전 인코더 약 0.7GB, 8k 컨텍스트 KV 캐시 약 1GB로 합계 약 7.5GB라 8GB에 겨우 들어간다. 3B는 여유가 있지만 표·차트의 숫자 전사 품질이 7B보다 눈에 띄게 낮다.
- 결정: 품질을 우선해 7B를 쓴다. 대신 컨텍스트를 4k로 줄여 KV 캐시를 절반으로 낮추고 GPU 상주 가능성을 높인다. 페이지 1장 캡셔닝은 비전 토큰 약 1,200개와 출력 500토큰 안팎이라 4k로 충분하다.
- 대가:
  1. 답변 단계에서 원본 페이지 이미지를 여러 장 넣을 수 없다. 이미지 투입 상한을 2장으로 두고 나머지 이미지 출신 청크는 캡션 텍스트로 대체한다.
  2. 캡셔닝 중에는 임베더·리랭커를 GPU에 올리지 않는다. 인덱싱은 "VLM 캡셔닝 → VLM 언로드 → GPU 임베딩" 순서로 분리 실행한다. 서빙 시점에는 VLM만 GPU, 임베더·리랭커는 CPU.
  3. 7B가 일부 CPU로 밀리면 페이지당 캡셔닝이 20초에서 40초 이상으로 늘 수 있다. Phase 0에서 실측하고, 40초를 넘기면 3B를 재검토한다.

- **추가 (2026-09-14, Phase 1 스모크 테스트 중 발견):** SDS KoPub 코퍼스의 실제 페이지 이미지는 약 300DPI(2480x3505px)로,
  원본 그대로 VLM에 넣으면 비전 토큰만 4,148개로 4k 컨텍스트를 초과해 요청이 거부됐다(실측 에러: `exceed_context_size_error`).
  `servers/vlm_client.py`에서 이미지의 긴 변을 1,280px로 다운스케일하는 전처리를 추가해 해결했다.
  대가: 매우 작은 글씨나 미세한 차트 눈금은 다운스케일 후 VLM이 잘못 읽을 수 있다 — 캡션 숫자 정확도 점검(Phase 1 검증)에서
  이 해상도로도 표 숫자를 정확히 읽는지 별도로 확인한다.

## D-04. 라우팅 4갈래와 병렬 캡셔닝: 12시간 → 1시간 (2026-09-14)

- 배경: 500페이지 스모크 테스트에서 캡셔닝이 장당 평균 11.9초였다. 전체 코퍼스의 이미지 경로 3,707장(9.1%)을
  순차 처리하면 약 12시간. 목표는 2시간 이내.
- 실측:
  1. 이미지 경로 3,707장 중 OCR 텍스트가 100자 이상인 페이지 1,387장. 스캔된 본문 페이지라 OCR로 검색 가능하다.
  2. 텍스트·OCR 모두 20자 미만인 페이지 1,478장. 표본 84장 중 80장이 400px 썸네일 기준 잉크 비율 0.2% 미만인 백지.
  3. 캡션 시간은 출력 길이가 지배한다. 프리필 1,592토큰은 1~3초, 생성은 초당 약 30토큰. 549토큰 페이지는 17.6초.
  4. Ollama 병렬 요청: 4요청에서 장당 3.7초, 6요청에서 3.5초로 포화. 최대 VRAM 6.66GB / 8GB.
  5. 이미지를 1024px로 줄이면 프리필이 1,173토큰으로 줄지만 장당 0.3초 이득. 작은 글씨 판독 위험 대비 이득이 작아 1,280px 유지.
- 결정:
  1. 라우팅을 네 갈래로 나눈다. 텍스트 ≥100자 → TEXT. 아니면 OCR ≥100자 → OCR(VLM 생략). 아니면 잉크 <0.2% → BLANK(인덱싱 제외). 그 외 → IMAGE(VLM).
  2. 캡셔닝을 병렬 4로 돌리고 출력을 400토큰으로 제한한다.
  3. 캡션은 JSONL 캐시에 즉시 기록해 중단 후 재실행 시 이어간다. 페이지 단위 실패는 재시도 1회 후 OCR/텍스트로 대체하고 전체를 멈추지 않는다.
  4. OCR 경로 페이지도 원본 이미지를 디스크에 남겨, 답변 단계에서는 VLM이 스캔 원본을 직접 본다.
- 예상: VLM 대상 약 900장 × 3.7초 ≈ 1시간.
- 대가:
  1. OCR 경로로 보낸 1,387장 안에 표가 있으면 OCR이 행·열 구조를 평탄화한다. VLM 캡션이었다면 구조가 보존됐을 것이다.
     시간이 남으면 이 페이지들을 2차 캡셔닝하는 옵션을 남긴다.
  2. 백지 판정 임계값(0.2%)은 84장 표본 기준이다. 옅은 워터마크 페이지나 연한 도장만 있는 페이지가 백지로 분류될 수 있다.
  3. 출력 400토큰 제한으로 매우 큰 표는 뒷부분이 잘릴 수 있다.

  안 보이는 값은 "수치 불명"/"판독 불가"로 쓰게 하며, 사진 속 캡션·낙서·도장 문구를 최우선으로 옮기게

- 검증: 문제였던 5장에 새 프롬프트를 그대로 재적용해 전부 정상화됨을 확인(광복군 포대 캡션 정상 인식,
  창작된 표 전부 사라짐, 목록을 표로 왜곡하지 않음). 이후 997장 전체를 새 프롬프트로 재캡셔닝했다.

- 997장 전체 재캡셔닝 후 통계: "수치 불명/판독 불가" 포함 3.6%(36장, 남발 아님), 표 포함 비율은
  13.0%(130장)에서 1.4%(14장)로 급감, 캡션 길이 중앙값 209자→84자.
- 표 비율 급감이 정보 손실인지 확인하기 위해 v1에서 표였던 페이지 8장을 무작위로 뽑아 v2와 나란히
  대조했다. 결과: 정보 손실이 아니라 형식 변화였다.
  - 실제 수치(예: 48.7%/51.3%)는 v1·v2 동일하게 정확히 보존됨.
  - v1에서 처음 확인한 추가 창작 패턴 2건을 이 대조에서 발견: (1) 존재하지 않는 `imgur.com` 이미지
    URL을 표 안에 지어 넣음(2개 페이지에서 반복), (2) 시스템 프롬프트 지시문 자체("영문 테이블 헤더는
    그대로... 숫자는 그대로...")가 캡션 본문에 새어나옴. v2에서는 두 문제 모두 사라짐.

    바뀐 것이 표 비율 급감의 주 원인이며, 내용 자체는 동일하게 유지됨.
  - 존재하지 않는 "차트 x축/y축/추세" 서술도 v2에서 사라짐.
- 대가: 페이지 제목을 영어로 임의 번역하는 새로운 사소한 습관이 1건 관찰됨(제목 전체 번역, 표 헤더
  번역 금지 지시와는 별개 사례). 정보 손실은 아니나 다음 점검 때 확인 필요.

## D-10. 생성 품질 채점 결과: 비교가 샘플링 편차에 묻힘 (2026-09-16)

- 배경: `eval/judge_rubric.md`를 사전등록한 뒤 15문항(text 5 · cross 5 · visual 5) x 2조건(ours: 원본 이미지
  투입 / baseline: 텍스트만)을 Claude Fable 5.1(이 세션)이 채점했다. 결과는 `eval/generation_report.json`.
- 집계: ours 평균 43.5점, baseline 48.1점. 유형별 text 45.2 vs 57.6, cross 40.8 vs 40.8, visual 44.4 vs 45.8.
  ours가 이긴 문항 5, baseline 7, 동률 3.
- 그러나 이 집계는 두 조건의 차이를 말해주지 않는다. `eval/gen_eval_image_usage.json`으로 확인한 결과
  **15문항 중 이미지가 실제로 VLM에 들어간 문항은 3개**뿐이고, 그중 정답 페이지 이미지가 들어간 건 1번
  하나다(12·15번은 5위 OCR 청크의 무관한 이미지). 나머지 12문항은 두 조건의 프롬프트가 글자 하나까지
  같다. 그런데도 점수가 평균 10.4점(최대 34점, 2번 문항 62 vs 96) 벌어졌다 — Ollama 기본 temperature(0.8)
  에서 나오는 순수 샘플링 편차다. 즉 단일 샘플 채점으로는 조건 간 5점 차이를 해석할 수 없다.
- 이미지가 실제로 들어간 3문항만 따로 보면:
  - 1번(정답 페이지가 IMAGE 경로, 이미지 = 정답 페이지): ours 80 vs baseline 73. 이미지가 도움됐다.
  - 12번(5위 OCR 청크의 무관 이미지 투입): ours 8 vs baseline 34. 무관한 이미지가 답을 크게 망쳤다
    (존재하지 않는 참고문헌 창작).
  - 15번(5위 OCR 무관 이미지): ours 71 vs baseline 60. 편차 범위 안.
- 채점에서 드러난 생성 단계 결함(조건과 무관하게 발생):
  1. **D-09의 500자 절단이 정답을 잘라냈다.** 8번(암보험 민원 통계 607/588/673건)은 수치가 청크
     1,238자 위치, 12번(한약재 면세 한도 300g·150g·3kg·6병)은 884~1,250자 위치에 있었다. 둘 다 정답
     페이지가 1위로 검색됐는데도 답을 못 냈다.
  2. **퇴행 출력.** 14번(정수기)은 두 조건 모두 `@@@@…`만 출력했다. 당시 점검에서는 이상 문자를 못 찾았으나
     (제어문자·제로폭 기준으로만 봤음), 이후 D-12에서 CJK 호환 한자 U+F9CA가 원인임을 확인했다.
  3. **자기모순 마감.** 3·4·6번에서 답을 써놓고 끝에 "문서에서 찾을 수 없습니다"를 덧붙였다.
     시스템 프롬프트의 기권 지시가 과잉 적용된다.
  4. **깨진 토큰.** "스트로미", "압구당시", "쿠알아이더 교육 기 hội" 같은 언어 혼입이 산발적으로 나온다.
  5. **차트 수치 접근 불가.** 11번(ODA 유상/무상 그래프)은 정답 페이지가 TEXT 경로라 이미지가 VLM에
     들어가지 않았고, 그래프 값(350 vs 210)은 추출 텍스트에 없다. 텍스트가 100자 이상이면 차트가 있어도
     이미지 경로로 가지 않는 라우팅(D-04)의 맹점이다.
- 결론: 이 15문항 채점은 "이미지 투입 효과"에 대해 n=1의 방향성 사례(1번)만 준다. 대신 생성 단계의
  구체적 결함 5가지를 찾아냈고, 그중 1·2·"무관 이미지" 문제는 D-11에서 바로 고친다.

## D-11. 답변 생성 수정: 동적 컨텍스트 예산, 이미지 상위 순위 제한, temperature 0 (2026-09-16)

- 배경: D-10의 결함 1(500자 절단), 12번 사례(무관 이미지), 샘플링 편차.
- 결정:
  1. 500자 고정 절단(D-09)을 폐기하고, 텍스트 글자 예산을 `num_ctx - 답변 예약(500) - 오버헤드(200)
     - 이미지당 1,500토큰 x 이미지 수`로 계산해 재랭킹 순서대로 채운다(글자/토큰 1.5 가정, 청크당 최대
     2,500자). 이미지가 없는 대부분의 질의에서 예산이 약 5,000자로 늘어난다.
  2. 이미지는 재랭킹 상위 2위 안의 청크만 투입한다(`answer_image_max_rank`).
  3. 답변 생성 temperature를 0으로 고정한다. 평가 재현성이 목적이며, 서빙 품질에도 해롭지 않다.
- 검증(`eval/gen_eval_refix_check.txt`): 글자 예산은 이미지 0장 5,094자 / 1장 2,844자 / 2장 594자.
  - 8번(암보험 민원 통계): 607·588·673건 3/3 적중. 500자 절단 때는 0/3이었다.

## D-12. 퇴행 출력 `@@@@…`의 원인: CJK 호환 한자 U+F9CA, NFKC 정규화와 자동 회복 (2026-09-16)

- 배경: 14번(정수기) 답변이 두 조건·temperature 0·0.8 모두 정확히 31개의 `@`였다. 원인을 단계적으로 좁혔다.
  1. 입력 변형 11종(줄바꿈 정규화, top-1 청크만, 시스템 프롬프트 제거, 질문만, 무관 청크, 질문 표현 변경 등)이
     전부 퇴행했고, "냉장고란 무엇인가?" 같은 컨트롤 단문까지 퇴행했다(`eval/gen_eval_q14_probe*.txt`).
     텍스트 전용 `qwen2.5:7b-instruct`는 정상. 이 구간의 응답은 모두 `usage.prompt_tokens == 0`이었다 —
     모델이 프롬프트를 처리하지 않고 반환한 것이다. Ollama 로그에는 같은 시간대(10:59)에 GPU 디스커버리
     워치독 타임아웃과 "unable to refresh free memory" 경고, 그 전(10:25)에 `llama-server terminated
     (exit status 1)` 크래시가 있었다.
  2. `ollama stop` 후 재로드하면 컨트롤 단문은 전부 정상. 그러나 14번 전체 프롬프트는 재시작 직후에도
     두 번 연속 퇴행했다(`eval/gen_eval_q14_after_restart.txt`). 즉 서버 저하와 별개로 이 프롬프트에
     결정적 트리거가 있다.
  3. 러너를 매번 새로 띄우고 이분했다(`eval/gen_eval_q14_bisect*.txt`, `gen_eval_q14_normalize.txt`):
     질문 단독 정상, 정수기 질문 + 정상 컨텍스트 정상, **정수기 본문 앞 200자만 붙이면 중립 질문으로도
     퇴행**(이때는 prompt_tokens=232로 처리된 뒤 퇴행). 뒤 120자에 트리거가 있었고, 줄바꿈·한자(U+4E00~9FFF)·
     중점 제거는 소용없었으며 **NFKC 정규화만 통과**했다.
  4. NFKC로 바뀌는 글자는 하나였다: "유입수(流入水)"의 **流 = U+F9CA, CJK COMPATIBILITY IDEOGRAPH-F9CA**.
     일반 한자 流(U+6D41)의 호환 코드포인트다. 한자 제거 정규식이 호환 한자 블록(U+F900~FAFF)을 안 덮어서
     3번 실험에서 살아남았다. 코퍼스 전체에서 2회, 2페이지에만 등장한다.
- 해석: Ollama/llama.cpp의 qwen2.5vl 토크나이저 경로가 이 호환 한자를 처리하지 못해 모델이 고정 토큰
  (`@` 반복)을 내는 것으로 보인다. 한 번 발생하면 이후 요청까지 `prompt_tokens=0`으로 퇴행하는 오염 상태가
  이어질 수 있고(NaN이 KV/프롬프트 캐시에 남는 방식으로 추정), 러너 재시작으로 회복된다. 텍스트 전용 모델은
  같은 글자를 정상 처리했다.
- 결정:
  1. `servers/answer.py`: 질문과 컨텍스트 텍스트를 VLM에 넣기 전에 NFKC 정규화한다(`normalize_for_vlm`).
     검증: 같은 200자를 NFKC만 적용해 넣으면 정상 요약이 나온다.
  2. `servers/vlm_client.py`: 퇴행 감지(글자 종류 2개 이하 또는 한 글자 80% 초과, 또는 `prompt_tokens == 0`)
     시 `ollama stop`으로 모델을 재시작하고 한 번 재시도한다. 두 번째도 퇴행이면 예외 → API 503.
     캡셔닝과 답변 생성 모두 적용. 단위 테스트 `tests/test_vlm_client.py`, `tests/test_answer.py`.
- 영향: D-10의 14번 0점(두 조건)은 모델 품질이 아니라 이 결함이다. `eval/generation_report.json`에 재분류하고,
  NFKC 적용 후 재생성한 답(`eval/gen_eval_q14_after_nfkc.txt`)으로 다시 채점한다.
- 대가: NFKC는 전각 영숫자·호환 기호도 함께 바꾼다(예: ㎏→kg, ①→1). 검색 임베딩은 원문 그대로 쓰므로
  영향이 없고 VLM 입력에만 적용된다. 트리거 글자가 희귀해(2/39,458) 재발은 드물겟지만, 다른 호환 문자도 같은
  문제를 일으킬 수 있어 감지·재시작 경로는 유지한다.

## D-08. Phase 3 검색 평가: SDS KoPub 라벨셋으로는 캡셔닝 효과를 검증할 수 없음 (2026-09-15)

- 배경: SDS KoPub VDR 600문항으로 `eval/retrieval_eval.py`를 만들어 judge 없이 자동 평가했다

  전체 결과: Recall@1 41.5%, Recall@5 77.0%, Recall@10 83.0%, MRR 0.564.

- "캡셔닝이 실제로 도움이 되는가"를 보려고, IMAGE 경로 페이지를 캡션 대신 OCR/텍스트로 채운
  베이스라인 벡터 저장소(`data/vector_store_baseline_ocr`)를 만들어 같은 600문항으로 재평가했다.
  전체 지표가 우리 파이프라인과 거의 동일하게 나왔다(Recall@1 41.3% vs 41.5%).
- 원인 규명: 600문항 중 **정답 페이지가 실제로 IMAGE 경로인 문항은 1개뿐**이다(OCR 경로 9개,
  나머지 590개는 TEXT 경로). "visual" 유형 161문항 중에서도 160개는 이미 텍스트가 100자 이상
  추출되는 페이지였다 — 차트가 있어도 주변 설명 텍스트가 충분하면 TEXT 경로로 라우팅되기 때문이다.
  즉 두 저장소는 599/600 문항에서 사실상 동일한 텍스트를 인덱싱한 것이라, 전체 지표가 같은 건
  당연한 결과이지 "캡셔닝이 무의미하다"는 근거가 아니다.
- IMAGE·OCR 경로가 정답인 10문항만 따로 뽑아 재비교했다(`eval/ablation_caption_vs_ocr.json`):
  - OCR 경로 9문항은 우리·베이스라인 순위가 전부 동일함(두 저장소가 같은 OCR 텍스트를 쓰므로
    당연함 — 비교 로직이 올바르다는 확인이기도 하다).
  - 라벨셋에서 유일한 IMAGE 경로 정답 문항: 우리 파이프라인은 1위로 찾았고, 베이스라인은
    top-10 안에서도 찾지 못했다. n=1이라 일반화할 수 없지만 방향은 설계 의도와 정확히 일치한다.
- 결론: SDS KoPub VDR은 검색 알고리즘(재랭킹, 임베딩 등) 비교에는 유효하지만, 이 프로젝트의
  핵심 가설인 "VLM 캡셔닝이 순수 텍스트 추출보다 낫다"를 검증하기에는 라벨 커버리지가
  구조적으로 부족하다(전체의 0.17%만 IMAGE 경로). 이 사실을 감추지 않고 그대로 보고한다.
- 후속 조치(남은 일로 이관): IMAGE 경로 997장 자체를 대상으로 한 질의셋을 직접 만들거나
  (문서 제목·주변 맥락에서 질의를 뽑아 자체 라벨링), DART 2차 코퍼스에서 표·차트 밀도가 높은
